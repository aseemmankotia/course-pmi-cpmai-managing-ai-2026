## Chapter 8: Model Technique Selection and QA/QC — Flashcards

| # | Front (Question) | Back (Answer) |
|---|-----------------|---------------|
| 1 | Supervised vs Unsupervised vs Reinforcement Learning — which needs labeled data? | Supervised = requires labeled input/output pairs. Unsupervised = no labels, finds patterns/clusters. Reinforcement = no labels, learns via reward signal from environment interaction. Exam tip: 'labeled historical outcomes' = supervised; 'discover hidden structure' = unsupervised; 'reward, trial-and-error, sequential decisions' = RL. |
| 2 | When should unsupervised learning be selected? | When no labeled data exists and the goal is pattern discovery: clustering (segmentation), anomaly detection (fraud/defects), dimensionality reduction. Exam tip: keyword 'no labels available' = unsupervised. |
| 3 | When should reinforcement learning be selected? | For sequential decision-making problems where an agent learns via trial-and-error and reward/penalty feedback (robotics, game strategy, dynamic pricing). Exam tip: keywords 'agent', 'environment', 'reward' = RL. |
| 4 | Complexity vs Interpretability trade-off | Higher complexity (deep nets, ensembles) usually raises performance but lowers interpretability ('black box'). Simpler models (linear regression, decision trees) trade some performance for transparency. Exam tip: regulated/high-stakes use cases favor interpretability. |
| 5 | Who selects the ML technique — PM or data scientist? | The AI project manager oversees the SELECTION PROCESS, ensuring alignment with business requirements (interpretability, cost, risk, latency), but the data scientist makes the technical algorithm choice. Exam tip: PM role = governance, not coding. |
| 6 | Typical train/test split convention | Common conventions: 70/30 or 80/20 train/test split. Smaller datasets often use k-fold cross-validation (commonly k=5 or k=10) for a more robust generalization estimate. Exam tip: cross-validation is preferred over a single split when data is limited. |
| 7 | Signs of overfitting during QA/QC | High training accuracy but significantly lower validation/test accuracy (large gap). Exam tip: classic trap = complex model + small dataset. Remedies: regularization, simpler model, more data, cross-validation. |
| 8 | Signs of underfitting during QA/QC | Low accuracy on BOTH training and test sets — model too simple to capture patterns. Exam tip: opposite pattern to overfitting; remedy is increasing model complexity or adding relevant features. |
| 9 | Core steps in a model QA/QC testing protocol | 1) Split data (train/validation/test). 2) Train model. 3) Evaluate metrics (accuracy, precision/recall, F1, AUC). 4) Bias/fairness testing across subgroups. 5) Robustness/adversarial testing. 6) Independent peer review before promotion. Exam tip: skipping bias testing is a common QA/QC failure scenario. |
| 10 | What belongs in model configuration management? | Version-controlled record of dataset version, code/algorithm version, hyperparameters, random seed, environment/dependencies, and the resulting model artifact. Exam tip: purpose is REPRODUCIBILITY and AUDITABILITY; 'just save the final model file' is a wrong-answer trap. |
| 11 | Peer review requirement before production deployment | An independent reviewer or review board (not the model's original developer) must validate performance, bias/fairness results, and documentation against pre-defined acceptance criteria. Exam tip: self-certification by the developer is a common wrong answer. |
| 12 | Performance vs Interpretability vs Complexity — 3-way trade-off | Simple models (linear/logistic regression, decision trees): low complexity, high interpretability, moderate performance. Ensemble/deep models: high complexity, low interpretability, typically higher performance. Exam tip: business requirement dictates which corner to prioritize — no universally 'best' technique. |
